## 1. 项目背景与目标

### 1.1 背景
求职者需要同时关注多个招聘网站的岗位信息，手工重复操作（搜索、筛选、逐站投递、跟踪状态）耗时且易遗漏。本系统面向**个人求职者**（非 HR/猎头），提供一套本地运行的桌面工具，自动完成：

1. 多招聘网站岗位信息的**定时增量采集**；
2. 个人账号的**登录会话管理**（扫码/短信，手动登录一次）；
3. **半自动简历投递**（程序完成机械操作，最终提交由用户确认）；
4. **多简历版本管理**（不同岗位使用不同简历）；
5. **大模型（LLM）辅助**：简历针对性优化、岗位匹配评分、投递策略建议等。

### 1.2 目标
- 数据全部存储在本地 SQLite，无服务器依赖；
- 操作全部在桌面 GUI 完成，界面友好；
- 登录态本地持久化，掉线后 GUI 提示、扫码重登即可；
- 投递以"半自动 + 风控"为默认，最大限度降低账号风险；
- AI 能力可插拔：未配置大模型时系统核心功能（采集/投递/跟踪）不受影响。

### 1.3 非目标
- 不做简历爬取（违反个人信息保护法，见 §12）；
- 不做全自动无人值守投递（默认关闭，风险自担的选项除外）；
- 不做云端部署/多用户。


### 3.1 AI 功能清单（F7 展开）

用户已提出 + 我方补充，全部通过可配置提示词实现：

| # | 功能 | 输入 | 输出 | 说明 |
|---|---|---|---|---|
| A1 | **简历针对性优化** | 岗位 JD + 当前简历 | 优化后的简历文本/建议 | 针对目标岗位调整亮点、关键词、表达 |
| A2 | **岗位匹配度评分** | 简历 + 岗位 | 评分(0-100) + 匹配理由 + 短板 | 岗位列表展示匹配分，辅助筛选 |
| A3 | **投递频次/策略建议** | 平台特征 + 用户活跃时段 + 历史投递 | 每日每站投递上限、时段建议 | 结合平台风控特点给出保守策略 |
| A4 | **招呼语/求职信生成** | 岗位 JD + 简历摘要 + 平台风格 | 打招呼语 / 求职信文本 | Boss 用简洁真诚的聊天式；其他站用正式投递信 |
| A5 | **岗位智能推荐** | 简历 + 近期采集岗位 | 推荐排序 Top N + 理由 | 从已采集库中按匹配度推荐 |
| A6 | **投递跟进话术** | 岗位 + 投递天数 | 跟进消息建议 | 投递 N 天未被查看时建议话术 |
| A7 | **面试问题预测** | 岗位 JD + 简历 | 高频面试题 + 回答要点 | 面试前准备 |
| A8 | **薪资行情分析** | 岗位关键词 + 城市 + 已采集数据 | 薪资分布统计与个人定位建议 | 用本地已采集数据做统计，AI 解读 |
| A9 | **周度投递复盘报告** | 一周投递/查看/面试记录 | 复盘总结 + 改进建议 | 每周生成 |

> 设计原则：AI 只做"辅助建议"，**不直接代替用户执行任何投递动作**。

## 6. 站点适配器设计（Collector 抽象）

每个站点一个适配器类，统一接口：

```python
class Collector(ABC):
    source: str                      # 站点标识

    # --- 登录 ---
    @abstractmethod
    def login_qr(self, page) -> bool: ...       # 扫码登录（如支持）
    @abstractmethod
    def login_sms(self, page, phone, code) -> bool: ...
    @abstractmethod
    def is_logged_in(self, page) -> bool: ...   # 会话有效性检测
    @abstractmethod
    def goto_login(self, page) -> None: ...

    # --- 采集 ---
    @abstractmethod
    def search_jobs(self, page, keyword, city, page_n) -> list[RawJob]: ...
    @abstractmethod
    def parse_job(self, page, url) -> RawJob: ...   # 详情页解析

    # --- 投递 ---
    @abstractmethod
    def open_apply(self, page, job) -> None: ...    # 打开投递页并预填
    @abstractmethod
    def submit_apply(self, page, resume) -> bool: ... # 最后一步提交（半自动触发）
    @abstractmethod
    def send_greeting(self, page, job, text) -> bool: ... # Boss 专用：发消息
```

- 各站登录细节（二维码定位、验证码输入框、登录成功判定）封装在适配器内；
- 站点差异（DOM 结构、接口签名、投递链路）只出现在适配器里，服务层完全与站点无关。

## 7. 登录模块设计（核心）

### 7.1 方案
采用**方案 A：Playwright 持久化浏览器上下文**：

- 每站点独立 `user_data_dir`（如 `data/browser/zhipin/`），Cookie + localStorage 自动持久化到本地磁盘；
- 登录一次后，后续启动自动恢复会话；
- 同时导出 `cookies.json` 备份，可手动清理/恢复。

### 7.2 统一登录流程

```
启动/切页 → 打开该站持久化上下文
        → 访问站点首页/个人中心
        ├─ is_logged_in() == True  → 状态灯 🟢，跳过
        └─ False → 打开登录页
                 ├─ 支持扫码 → 截取二维码 → GUI 显示（实时刷新防过期）
                 │            用户手机 App 扫码 → 轮询 is_logged_in()
                 ├─ 支持短信 → GUI 输入手机号 → 触发发送
                 │            用户输入验证码 → 提交
                 └─ 登录成功 → 保存会话 → 状态灯 🟢
```

### 7.3 会话保活与失效处理

| 场景 | 处理 |
|---|---|
| 启动校验 | 每站访问个人中心页，被重定向到登录页 = 失效 |
| 失效提示 | GUI 状态灯变 🔴，提示"请重新扫码/登录"；不强制自动重登 |
| 运行中掉线 | 投递前二次校验会话，失效则中断该操作并提示 |
| 异地/风控 | 登录后固定本机 IP 使用，不换 IP 高频操作 |

### 7.4 状态管理（GUI 登录中心）

每站点一张卡片：站点名 + 状态灯（🟢已登录 / 🟡校验中 / 🔴未登录）+ 操作按钮（登录/重新登录/退出登录/查看会话信息）。

## 8. 采集模块设计

### 8.1 搜索任务配置（GUI 可编辑，存 `search_tasks` 表）
- 站点多选；
- 关键词（多个，如 ["Java开发", "后端开发"]）；
- 城市（多个，如 ["北京", "上海"]）；
- 薪资区间（可选）；
- 启用/停用开关。

### 8.2 采集流程
```
任务运行 → 遍历启用的任务 → 遍历站点 → 遍历关键词×城市
        → search_jobs 翻页采集列表 → 逐条 parse_job 抓详情
        → 字段归一化 → upsert 到 jobs 表 → 记录 crawl_runs
```

### 8.3 增量更新策略
- 唯一键 `(source, job_id)` 做 UPSERT：新岗位插入，已存在则更新（薪资/状态），列表缺失的标记 `offline`；
- 每次运行记录 `crawl_runs`（抓到/新增/失败数），GUI 可见；
- 每日定时（默认早 8:00）增量采集，只处理近 N 天发布的岗位（默认 7 天，可配）。

### 8.4 字段归一化（统一 schema）

| 字段 | 类型 | 说明 |
|---|---|---|
| source | TEXT | 站点标识 |
| job_id | TEXT | 源站岗位 ID |
| title | TEXT | 岗位名称 |
| company | TEXT | 公司名称 |
| company_size | TEXT | 公司规模 |
| industry | TEXT | 行业 |
| salary_min / salary_max | INTEGER | 月薪（千元） |
| salary_raw | TEXT | 原始薪资文本 |
| city / district | TEXT | 城市 / 区 |
| experience | TEXT | 经验要求 |
| education | TEXT | 学历要求 |
| tags | TEXT | 标签（JSON） |
| description | TEXT | 岗位描述（AI 输入源） |
| publish_date | TEXT | 发布日期 |
| job_url | TEXT | 岗位链接 |
| crawl_time | TEXT | 采集时间 |
| status | TEXT | active / offline |
| is_favorite | INTEGER | 收藏标记 |
| match_score | REAL | AI 匹配分（缓存） |

## 9. 投递模块设计

### 9.1 模式
**半自动（默认，推荐）**——程序完成所有机械操作，**最终提交必须用户确认**：

```
岗位列表勾选 → 选简历版本 → 点击"开始投递"
→ 程序打开该岗位投递页 → 自动选好简历/预填表单
→ GUI 弹出确认框（显示岗位+简历版本+平台）→ 用户点"确认投递"
→ 程序执行最后一步提交 → 写入 applications 记录 → 下一条
```

Boss 直聘特殊链路：打开与 HR 的沟通窗口 → 预填打招呼语（可 AI 生成）→ 用户点"发送"。

### 9.2 风控策略（内置，全自动模式也强制生效）
- 默认**人工确认模式**；
- 可选"全自动模式"开关（默认关闭）：用户自担风险；
- 频率控制（无论哪种模式都执行）：
  - 每日每站投递上限（默认 20，AI 可给建议值）；
  - 两次投递随机间隔 30~90 秒；
  - 只在配置的时间窗内运行（默认 09:00–21:00）；
  - Boss 每日沟通上限更保守（默认 10）；
- 投递前二次校验登录态，失效立即中断。

### 9.3 投递记录与状态跟踪（applications 表）
| 字段 | 说明 |
|---|---|
| job_ref_id | 关联 jobs.id |
| source | 站点 |
| resume_version | 使用的简历版本名 |
| applied_at | 投递时间 |
| status | submitted / viewed / chatting / interview / rejected / closed |
| note | 备注（如跟进日期） |

GUI 投递中心：待投递队列、投递历史表、状态更新、备注。

## 10. 简历管理模块（多简历）

- 支持多份简历版本（如"Java 开发版""产品经理版"），每份含：版本名、目标岗位、文件路径、解析文本；
- 支持 PDF / Word 上传，程序用 pypdf / python-docx 提取文本，供 AI 功能使用；
- 投递时选择简历版本，默认用匹配该岗位关键词的版本（也可 AI 建议）；
- AI 优化的简历可导出为新版本，不覆盖原版。

## 11. AI（大模型）模块设计

### 11.1 配置（GUI AI 设置页）
| 配置项 | 说明 |
|---|---|
| 启用开关 | 关闭时其余功能不受影响 |
| API Base URL | 兼容 OpenAI 协议，如 DeepSeek / 通义 / 本地 Ollama |
| API Key | 本地存储（加密或明文随用户选择） |
| 模型名 | 如 deepseek-chat / gpt-4o-mini 等 |
| 温度 | 默认 0.7 |
| 超时/重试 | 默认 30s / 2 次 |

### 11.2 提示词管理
- 每个 AI 功能对应一条可编辑提示词（存 `prompts` 表）；
- 系统提示词（角色设定）+ 用户提示词模板（含 `{jd}`、`{resume}`、`{platform}` 等占位符）；
- GUI 可编辑、恢复默认、测试调用。

### 11.3 功能调用流程（以 A1 简历优化为例）
```
用户触发（岗位列表 → "AI 优化简历"）
→ AiService 读取 prompts[resume_optimize] + 填充占位符
→ 调用 LLM（openai 兼容 SDK）
→ 流式/一次性返回结果 → GUI 展示对比 → 用户选择"另存为新简历版本"
```

### 11.4 各功能提示词设计要点

| 功能 | 系统提示词角色 | 输出格式约定 |
|---|---|---|
| A1 简历优化 | 资深 HR/简历顾问 | Markdown 分节：亮点改写、关键词补充、删除建议 |
| A2 匹配评分 | 招聘专家 | JSON：`{"score": 0-100, "reasons": [...], "gaps": [...]}` |
| A3 投递策略 | 平台风控分析师 | 每日上限、时段、节奏建议（保守优先） |
| A4 招呼语 | 求职沟通顾问 | 按平台风格：Boss 口语化≤50字；其他正式求职信 |
| A5 岗位推荐 | 职业顾问 | 排序 TopN + 理由 |
| A6 跟进话术 | 沟通顾问 | 按投递天数分档话术 |
| A7 面试预测 | 面试教练 | 高频题 + 回答要点 |
| A8 薪资分析 | 薪酬分析师 | 分布解读 + 个人定位建议 |
| A9 复盘报告 | 求职教练 | 周度总结 + 改进项 |

| 表 | 用途 |
|---|---|
| jobs | 岗位主表（§8.4 字段） |
| applications | 投递记录（§9.3 字段） |
| resumes | 简历库（id, name, target_title, file_path, content, created_at, updated_at） |
| ai_settings | 单行大模型配置（id=1, base_url, api_key, model, temperature, enabled） |
| prompts | 提示词（feature 唯一, name, content, enabled） |
| search_tasks | 搜索任务（§8.1） |
| crawl_runs | 采集运行记录（task_id, started_at, finished_at, fetched, inserted, status, error） |
| settings | 通用设置（投递上限、时间窗、随机间隔、默认简历等，key-value） |

### 12.2 关键约束
- `jobs`：`UNIQUE(source, job_id)`；`publish_date`、`source`、`city` 建索引；
- `applications`：`UNIQUE(job_ref_id)`（同一岗位不重复投递）；
- 外键：`applications.job_ref_id → jobs.id`；
- 迁移：启动时检查 schema 版本，自动执行增量 DDL。

## 14. 调度设计

- APScheduler（BackgroundScheduler）随应用启动；
- 默认任务：每天 08:00 增量采集所有启用任务；
- 可在 GUI 修改运行时间、开关；
- 采集任务结束后自动清理 `crawl_runs` 过期记录（保留 90 天）。

## 15. 风控与合规

| 类别 | 说明 |
|---|---|
| 频率控制 | 每站请求间隔随机化、每日上限、时间窗（§9.2） |
| 行为拟真 | Playwright 真实浏览器、随机等待、必要时拟人化输入 |
| 登录态保护 | 固定本机使用、避免频繁换 IP、避免高频重登 |
| 平台协议 | 岗位信息属公开数据，采集风险低；投递行为受平台协议约束，采用半自动 + 低频率 |
| 个人信息 | 简历数据全部本地存储，不采集他人简历；本工具只投递用户自己的简历 |
| 数据保留 | 岗位数据保留 90 天可配；用户可一键清空 |

## 16. 安全与隐私

- SQLite 单文件本地存储，无网络上传（除 LLM API 调用外）；
- LLM API Key 本地保存（提供明文/系统凭据两种选项，明文默认并提示风险）；
- 上传给 LLM 的数据仅限用户主动触发的功能所需内容（JD + 简历文本），可随时在设置中关闭 AI；
- `user_data_dir` 与 `app.db` 位于 `data/`，不提交版本库。
